Candidate 01

Lift the sequencer out of the player

A pure PlaybackCursor module owning playlist, queue, shuffle order and repeat — leaving the player as the adapter over just_audio.

STRONG

Files

  • lib/services/audio_player_service.dart 894
  • test/services/audio_player_service_sequencing_test.dart 425
  • test/services/audio_player_service_replaygain_test.dart 55

Problem

One module holds five unrelated concerns: cursor arithmetic (_nextPlaylistIndex, _shuffleOrder, _playingFromQueue), source construction (LockCachingAudioSource + 2 GB eviction), load orchestration (debounce, _loadToken, retry-on-stall, drop recovery), platform presence (SMTC, wakelock, window title, audio_service) and ReplayGain. Its interface has grown to roughly 40 public members.

The tests are the evidence. The cursor arithmetic is pure — no I/O, no player — but it can only be reached through seedForTest, nextPlaylistIndexForTest, prevPlaylistIndexForTest, regenerateShuffleOrderForTest, shuffleOrderForTest, shufflePosForTest and replayGainFactorForTest. 425 lines of sequencing tests never call a production entry point. When tests have to be let in through a side door, the interface is not the test surface — and the module is the wrong shape.

Solution

Move the cursor state — _playlist, _currentIndex, _queue, _shuffleOrder, _shufflePos, _playingFromQueue, _isShuffleEnabled, _repeatMode — into a plain Dart class with no Flutter and no just_audio import. Its interface answers one question: which track next, and why. 

class PlaybackCursor {
  Track? get current;
  Track? peekNext();          // no mutation
  Track? advance();           // queue > playlist > null
  Track? rewind();
  Track? jumpToQueued(int i);
  Track? jumpToUpcoming(int i);
  void  start(List<Track> ctx, {int at, bool shuffled});
  void  enqueue / dequeue / move / reorderUpcoming;
  List<Track> get upcoming;
  set shuffle / repeat;
}

AudioPlayerService keeps its public API unchanged and delegates: playNext() becomes _selectAndPlay(_cursor.advance()). All seven *ForTest members are deleted.

Benefits

  • locality · Every "what plays next" rule lands in one file. Today a queue-vs-shuffle question is answered by reading six methods spread over 300 lines and correlating three fields.
  • leverage · Callers learn one verb per intent instead of the current pairs (toggleShuffle() then playPlaylist(t, -1) — see Candidate 02).
  • tests · The existing 425 lines survive almost verbatim, re-pointed at real methods. seedForTest is replaced by a constructor. The deletion test passes clearly: delete PlaybackCursor and the same complexity reappears immediately inside the player.
  • platform · Cursor tests stop needing a fake audio backend at all, so sequencing regressions are caught identically on Windows and Android.
⚠ Relationship to docs/decisions.md

Does not contradict "Track sequencing is hand-rolled in Dart, not ConcatenatingAudioSource". It is the opposite: giving the hand-rolled sequencer its own module makes that decision cheaper to keep, and makes the eventual reversal (if just_audio_media_kit ever fixes concatenating sources) a single-file deletion rather than surgery through the player.

Candidate 02

Give the player one verb per play intent

The "shuffle this folder" ritual is hand-assembled at 6 call sites across 5 files.

STRONG

Files

  • home_screen.dart :170 :362 :488
  • all_tracks_screen.dart :161
  • folder_detail_screen.dart :123
  • tv_home_screen.dart :70
  • audio_player_service.dart playPlaylist / toggleShuffle

Problem

There is no "shuffle-play these tracks" verb, so every screen assembles one out of two lower-level operations plus a magic sentinel: 

if (!playerService.isShuffleEnabled) {
  playerService.toggleShuffle();
}
playerService.playPlaylist(tracks, -1);   // -1 = "pick a random start"

Three facts a caller must know that the interface does not state: that -1 means random start; that it only randomises if shuffle happens to be on; and that flipping shuffle is a persistent mode change, not a property of this play. The read-then-toggle guard exists purely to work around toggleShuffle() having no setter form. Every new entry point copies the incantation, and a future change to shuffle semantics has to find all six.

Solution

Replace the sentinel with intent-named entry points on the player (backed by PlaybackCursor.start from Candidate 01), and add a plain setter: 

Future<void> play(List<Track> tracks, {int from = 0});
Future<void> playShuffled(List<Track> tracks);
void          setShuffle(bool enabled);

Six call sites collapse to playerService.playShuffled(tracks). The screens stop knowing anything about shuffle bookkeeping. The same treatment applies to the Navigator.push(PlayerScreen) that follows every one of them — a playAndOpen helper, or a single navigation call site.

Benefits

  • leverage · One verb replaces a four-line protocol plus two undocumented invariants.
  • locality · "What does shuffle-play mean" becomes a single method, not six copies that can drift.
  • tests · Directly testable through the public interface once Candidate 01 lands — "playShuffled anchors the first track and does not repeat until exhausted" is one test, not an inference across screens.

Candidate 03

One CoverArt widget

The same six-fact cover-art incantation is retyped at 6 render sites, and the URL/cache-key pair is duplicated across two models.

STRONG

Files

  • home_screen.dart :517 :562 :647
  • all_tracks_screen.dart :378
  • folder_detail_screen.dart :424 :550
  • models/track.dart coverUrl · coverCacheKey
  • models/folder.dart coverUrl · coverCacheKey (identical)

Problem

To render one cover, a screen must independently know all of: multiply the logical size by devicePixelRatioOf(context); round it; pass that same number to both coverUrl(size:) and coverCacheKey(size:) or the cache silently misses; null-check coverArtUrl first because coverUrl is force-unwrapped with !; wrap in ClipRRect(radius: 4); and supply the Icon(Icons.music_note, size: 48) fallback twice — once as errorWidget, once as the null branch.

That is six facts × six sites. It has already drifted: the 48 * dpr expression is written out twice per site (once for the URL, once for the key), so the two can fall out of step in a single-character edit — and the resulting bug is invisible (a 100% cache miss, not a crash). It is the same failure mode decisions.md already documents for the Android stream cache, reappearing in the image cache.

Solution

// lib/widgets/cover_art.dart
CoverArt(this.source, {required this.size, this.radius = 4});
// source: anything with a coverArtId — Track or Folder

Every render site becomes CoverArt(track, size: 48). The dpr multiply, the shared rounded pixel size, the cache key, the clip and the fallback all move inside — where a caller can no longer get them out of sync. Pair it with a small CoverArtRef mixin (or a shared value type) so Track and Folder stop carrying two identical copies of coverUrl/coverCacheKey.

Benefits

  • leverage · Interface drops from six facts to two (what and how big).
  • locality · The image-cache budget set in main.dart (50 MB / 300 entries) is tuned against a working-set assumption that only holds if every site sizes covers consistently. One widget makes that enforceable instead of aspirational.
  • tests · "URL size and cache-key size always agree" becomes one widget test instead of six unwritten ones.

Candidate 04

One track tile, not three

Three near-identical tiles have already drifted — the home screen silently lost swipe-to-queue.

STRONG

Files

  • home_screen.dart :630 _TrackTile
  • all_tracks_screen.dart :314 _AllTracksTile
  • folder_detail_screen.dart :482 _FolderTrackTile

Problem

All three are private classes with the same body: a Selector<AudioPlayerService, String?> on currentTrack?.id, blue-and-bold styling for the current track, an Icons.equalizer trailing marker, the cover-art block from Candidate 03, and formattedDuration as subtitle.

Drift already happened. One public TrackTile in lib/widgets/, with the two genuine variations as parameters — a nullable leadingIndex (all-tracks numbers its rows) and swipeToQueue (default true). Everything else — the selector, the current-track styling, the cover, the queue gesture and its snackbar — lives inside.

Benefits

  • locality · Fixes the missing home-screen gesture as a side effect, and makes the next tile change land everywhere by construction.
  • leverage · ~180 lines of near-duplicate widget code collapse to one ~70-line widget plus three call sites.
  • tests · Currently untestable — private classes inside screen files, so the existing screen tests can only reach them through a full screen pump. A public widget gets direct tests for "shows the equalizer marker for the current track" and "swipe enqueues".

Candidate 05

Let Track own every way it is built

Three construction paths, one of them hand-inlined in the scanner — and it has already lost a field.

STRONG

Files

  • models/track.dart fromSubsonic · fromJson
  • services/library_scanner.dart :97–118 inline Track(...)

Problem

LibraryScanner.scan() builds Track objects by hand from Navidrome's native API payload, in a loop in the middle of a scan method. It is a third parser, living outside the model, and it disagrees with the other two on every key name — because the native API genuinely uses different ones:

That last row is the drift. folderName is computed in fromSubsonic and persisted by toJson, but the scanner path — the one that produces the entire library on every launch — leaves it empty. The knowledge of "how a payload becomes a Track" is spread across two files and three shapes, so a new field has three places to be added and two chances to be forgotten.

Solution

Add Track.fromNativeApi(json, api) next to its two siblings and have the scanner call it. All three factories then sit side by side in one file, where the field-by-field differences are visible at a glance and a missing folderName is obvious rather than buried in a loop 100 lines into a scan method.

Benefits

  • locality · One file answers "where do Tracks come from". Adding a field means editing three adjacent factories, not hunting a third one in a service.
  • tests · track_test.dart already covers the two factories it can reach (211 lines). The native path — the one that builds the whole library — has no test because it isn't addressable. A factory makes it a three-line test.
  • leverage · LibraryScanner.scan() sheds ~25 lines of parsing and goes back to being about scanning.

Candidate 06

A NowPlayingPresence seam

Two adapters already exist for "tell the OS what is playing" — but there is no seam between them, only if (_isWindows).

WORTH EXPLORING

Files

  • audio_player_service.dart _isWindows/_isAndroid, 4 sites
  • windows_media_controls_service.dart 234
  • windows_wakelock.dart 58
  • audio_handler.dart 194

Problem

The same concept — the OS should show this track and these transport controls — is implemented twice, and the player interleaves both inline. Windows work happens through _updateWindowsMetadata, a lazily-initialised singleton, a windowManager.setTitle call and a wakelock toggle inside the playingStream listener. Android work happens through an optional MusicAudioHandler? threaded in via the constructor and null-checked at each use. There is no common vocabulary, so the two paths cannot be reasoned about together — and neither can be exercised without the platform it targets.

The rule applies cleanly here: one adapter is a hypothetical seam; two adapters is a real one. Two already exist.

Solution

abstract class NowPlayingPresence {
  void bind(PlaybackCommands c);  // play/pause/next/prev/stop
  void show(Track t);
  void setPlaying(bool playing);
  void clear();
}
// WindowsPresence — SMTC + taskbar + title + wakelock
// AndroidPresence — audio_service handler
// NoPresence      — const no-op; the default in tests

The player calls four methods unconditionally. Every if (_isWindows) and every _audioHandler != null check disappears from playback code.

Benefits

  • tests · The biggest win. playback_test.dart currently has to mock the raw window_manager MethodChannel — with a comment explaining that _updateWindowsMetadata calls it unguarded — purely to stop an unrelated test from throwing. A NoPresence default deletes that workaround; a recording fake turns "starting a track shows it to the OS" into an assertion.
  • locality · Platform reality is confined to three small adapters instead of being woven through the hottest file in the repo — which is exactly what CLAUDE.md warns is expensive to verify (a change proven on one platform says little about the other).
  • leverage · iOS or Linux presence becomes a new adapter, not a new branch.

Candidate 07

Stop baking credentials into the models

Track and Folder import SubsonicApiService so every instance can carry a pre-signed URL.

WORTH EXPLORING

Files

  • models/track.dart :1 imports the api
  • models/folder.dart :1 imports the api
  • library_cache.dart · library_scanner.dart thread api: through

Problem

The dependency points the wrong way: the domain model depends on the transport. Every construction site must thread an api: argument through — including LibraryCache.load, whose only reason to take a SubsonicApiService is to re-mint URLs. And the consequence is that every Track in memory holds a live, password-equivalent token+salt in streamUrl and coverArtUrl, for the whole session, for the whole library.

Two smaller consequences follow. Model tests need an api stand-in to build a fixture. And the URLs are minted once at parse time but described in the player's comments as rotating per request — a mismatch that is easy to reason wrongly about.

Solution

Make Track and Folder plain data holding id and coverArtId only, and introduce a StreamUrlResolver (implemented by SubsonicApiService) that the player and the CoverArt widget consult at the moment of use. Models stop importing services; the arrow reverses.

⚠ Relationship to docs/decisions.md

This extends the 2026-08 decision "Cached cover art stores the id, not the resolved URL" rather than contradicting it. That decision removed the credential from the file on disk; schema v3 enforces it. This candidate applies the same reasoning to the copy in memory. Nothing about the security floor changes — the id stays the thing that is stored, and the URL stays the thing that is derived. Note the decision file states the reversal condition as "nothing — this is a security floor", so any exploration here must preserve id-only persistence.

Benefits

  • locality · One module owns URL signing. Today it is SubsonicApiService plus two models plus the cache plus the scanner.
  • tests · sampleTrack() fixtures stop needing a fake api. LibraryCache tests stop constructing one.
  • leverage · A future auth change (expiry, refresh, a different scheme) touches the resolver, not every parse site.

Candidate 08

Two screen rituals worth a widget each

"Follow the playing track" is copied verbatim; "wait for the scanner" is re-improvised per screen.

SPECULATIVE

Files

  • all_tracks_screen.dart _followCurrentTrack, _onScannerUpdate
  • folder_detail_screen.dart _followCurrentTrack, _leadingRowCount
  • home_screen.dart _onScannerChanged

Problem

Follow-the-playing-track is ~35 lines duplicated near-verbatim in two screens: the same _followedTrackId guard, the same isAttached check, the same alignment: 0.3 and 400 ms easing, the same listener add/remove with a bare try/catch in dispose. Only the index mapping differs (folder_detail offsets by _leadingRowCount).

Waiting for the scanner is improvised three different ways: home subscribes in a post-frame callback and holds its own _scannerForListener field; all_tracks subscribes conditionally on hasInitialData and unsubscribes from inside the callback; folder_detail reads once and never listens at all — so it will not update if a background refresh lands while it is open.

Solution

A FollowingTrackList wrapper taking the tracks, an indexOffset and an item builder; and a LibraryData builder widget that resolves the cache-then-refresh states (loading / ready / error / staleWithRefreshError) once, so screens switch on a state instead of wiring listeners.

Marked speculative because both are UI plumbing with real per-screen variation, and the payoff is smaller than Candidates 01–05. Worth doing after the tile and cover-art work, when the remaining per-screen differences are visible rather than buried.

Benefits

  • locality · Scroll-following behaviour becomes one testable widget rather than two copies that must be kept in step by hand.
  • tests · The folder_detail "does not refresh on background scan" gap becomes visible as a state the builder must handle, not an omission nobody notices.

Top recommendation

Start with Candidate 01 — lift the sequencer out of the player

It is where the work actually happens. audio_player_service.dart is both the most-changed file in the history (12 commits) and the largest (894 lines). Deepening pays off in proportion to how often a module is touched, and this one is touched more than anything else in the repo.

The evidence is unambiguous, not a matter of taste. Most architecture arguments come down to preference. This one does not: there are seven @visibleForTesting holes in the wall and a 425-line test file that never calls a production method. The tests have already told you where the seam belongs — the refactor just moves the wall to where the tests are standing.

It protects something load-bearing. CLAUDE.md lists manual sequencing first among the things not to "simplify", and decisions.md explains why. Right now that decision is defended by comments. Given its own module with its own tests, it is defended by structure — and the day just_audio_media_kit fixes concatenating sources, reversing it is deleting one file instead of unpicking a 894-line class.

It unblocks the rest. Candidate 02 needs PlaybackCursor.start(shuffled:) to exist before playShuffled is more than a wrapper. Candidate 06 is far easier once playback code is no longer interleaved with cursor bookkeeping.

One caution. The behaviour being moved is genuinely subtle — queue-over-playlist priority, shuffle anchoring on regenerate, the _playingFromQueue return-to-playlist rule, repeat-all wraparound in both directions. Port the existing 425 lines of tests first, re-pointed at the new interface, and let them stay green through the move. And per CLAUDE.md: verify on Windows and Android before calling it done — flutter test passing says nothing about either audio backend.
